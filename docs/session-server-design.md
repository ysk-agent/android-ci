# Session CI server — design draft (layer 3)

Status: design draft, committed to this repo 2026-11-21 as the shared
policy record for both Muses (see "Shared between moka and mio").
Not yet implemented. The reachability spike succeeded the same day
(see below).

## Shared between moka and mio (Yosuke, 2026-11-21)

Making this usable from Mio as well as Moka is a requirement, not an
afterthought:

- This repo is the single source of truth for the convention and the
  design; both Muses read the same current version here instead of
  relying on chat history.
- Nothing in the server or the client is Moka-specific. Mio's VM
  (muse-1) is a tailnet member with the same tunnel route, so she can
  discover sessions from her own `tailscale status`, dispatch session
  workflows against this repo, and submit jobs exactly as Moka does.
- The per-session token is generated by whichever Muse starts the
  session, so no credential needs to be shared between them; the only
  shared secret is `TS_AUTHKEY`, held by the repo, not by an agent.
- The session pool is shared in effect: sessions started by one Muse
  are visible to the other through the tailnet peer list, so the
  client must tolerate sessions it did not start (and label the
  starter in `/health`).

## Goal

One shared, ~1-hour-lived GitHub Actions session that Moka can ask to
`git fetch` + build + test any of the Android repos in a warm workspace
with an already-running emulator, so the per-iteration fixed costs
(runner start, checkout, Gradle/AVD cache restore, emulator boot) are
paid once per session instead of once per push.

## Non-goals

- Not a replacement for formal per-repo CI. A warm workspace and a
  long-lived emulator can hide problems that only appear from a clean
  state, so the push-triggered CI stays as the release gate.
- Not a persistent service. It lives for one session, then the runner
  and its ephemeral tailnet node disappear.

## What the spike proved (2026-11-21)

- Run 44878377495 joined the tailnet as `android-ci-spike` via
  `tailscale/github-action` v4 and Moka's VM received HTTP 200 from
  `/health` through the tunnel proxy. The Tailscale route works; the
  polling fallback is not needed.
- Two spike lessons are baked into this design:
  - v4 sets `--hostname` itself — pass the hostname through the
    action's dedicated `hostname` input, never via `args`
    (run 44878187967 failed on the duplicate flag).
  - The node address can be learned from the VM's own `tailscale
    status` peer list, so session discovery does not depend on the
    Mac being reachable.
- The `TS_AUTHKEY` secret (Reusable + Ephemeral) is already registered
  in `ysk-agent/android-ci`. No key is ever pasted in chat or committed
  to the repo, and no tailnet address is written into the repo.

## Session lifecycle

1. **Start.** Moka runs `gh workflow run ci-session.yml` with dispatch
   inputs: `lifetime_minutes` (default 60, max 360 — the Actions job
   cap), `warm_repos` (default: `yt-client` only, see decision 3),
   and a one-time `session_token` it generates (see Auth).
2. **Warm-up (once).** The job joins the tailnet as
   `android-ci-session`, starts the server on port 8765, checks out
   each warm repo at its default branch, runs one warm-up build per
   repo (Gradle daemon stays resident), and boots one shared emulator
   (see Emulator). It then prints readiness to the step summary.
3. **Serve.** Moka discovers the node from `tailscale status`,
   checks `/health`, and submits jobs. The server processes **one job
   at a time** (serial queue — a single emulator cannot run two app
   tests at once). Further requests wait in the queue.
4. **End.** The lifetime is **activity-based** (Yosuke, 2026-11-21):
   the 60 minutes count from the last activity, not from session
   start. A job submission, a job still running or queued, and a
   re-fetch all reset the clock, and the session never dies mid-job.
   The session exits when 60 minutes pass with no activity, or Moka
   calls `POST /shutdown`; the runner and its ephemeral node then
   disappear. The Actions job cap (360 min) is the absolute backstop,
   with `timeout-minutes` set slightly above the requested lifetime.
   (This absorbs the earlier separate 10-minute idle timeout: the
   activity window *is* the idle rule.)

## API (stdlib-only Python, port 8765, same shape as the spike server)

- `GET /health` → `200 {"status": "ok", ...}` (unchanged from the spike).
- `POST /jobs` with JSON body:
  `{"repo": "yt-client", "ref": "<sha or branch>", "scope": "player",
  "command": "build+test"}`. Returns `{"job_id": "...", "state":
  "queued"}` immediately — job submission never blocks on a build.
  `scope` reuses the layer-2 test-scope convention
  (`all|player|feed|none`, per-app section meanings); the caller
  must name it, there is no commit-marker parsing in the session.
- `GET /jobs/{id}` → state (`queued|running|passed|failed`),
  exit code, duration, and a short result summary.
- `GET /jobs/{id}/log` → the full build/test log (plain text).
- `GET /jobs/{id}/apk` → the built debug APK for that job, fetched
  over the tailnet on demand (verification-scale traffic only).
- `POST /shutdown` → orderly end of the session.

Why async jobs instead of one long synchronous request: a build+test
run takes minutes, and a synchronous HTTP call would sit through
proxy and client timeouts. Submit-then-poll keeps each request short
and lets Moka watch several queued jobs from one place.

## Parallelism (added 2026-11-21, Yosuke's point)

Within one session, jobs stay serial (one emulator). But nothing
limits us to one session: several session jobs can run at once, each
with its own runner, emulator and ephemeral tailnet node, so testing
parallelises **across sessions**:

- different repos at the same time (yt-client while apps-updater runs);
- the same repo's scopes split across sessions (player in one, feed in
  another) when a change is large enough to want both quickly;
- a long `all` run no longer blocks quick `none`/`feed` iterations —
  they go to a second session instead of queueing behind it.

Design consequences:

- Hostnames must be unique per session (`android-ci-session-<suffix>`);
  discovery lists every matching node in `tailscale status`.
- The client tracks sessions as a small pool: submit to an idle
  session, start another when all are busy and the work justifies it.
- Each extra session pays its own warm-up once, so parallelism is for
  genuinely independent work, not a default for every job.
- The practical ceiling is GitHub's concurrent-job allowance for the
  account, not anything in this design: on the Free plan that is 20
  concurrent jobs account-wide (GitHub Docs, Actions limits), shared
  with any formal CI running at the same time. Realistic usage is
  3–5 sessions (Yosuke's estimate, 2026-11-21), so the client caps
  its session pool at 5 by default — far under the account limit,
  leaving the formal CI room to run.

## Workspaces

- One checkout per repo under the session workdir, created at warm-up
  (warm repos) or lazily on first use (other repos). A job runs
  `git fetch` + `git checkout <ref>` in that repo's directory, then
  an incremental build with the resident Gradle daemon.
- Repos in scope (from the android-ci README): yt-client,
  apps-updater, yt-player, findmy-mac, moka-vpn, phone-node.
  moka-vpn is the awkward one: its libtailscale AAR cache miss costs
  8–9 minutes, so its warm-up build matters most — but it also makes
  the session start slowest if warmed eagerly (see decision 3).
- Stale-state rule, stated up front: if a session result looks
  suspicious, or before any release, re-run the formal per-repo CI.
  The session never certifies a release.

## Emulator

- One shared emulator for the whole session: API 35, `pixel_6`,
  `x86_64`, `-no-window -gpu swiftshader_indirect -noaudio
  -no-boot-anim`, started once at warm-up. This is not a guess:
  yt-client's `build.yml` and apps-updater's
  `emulator-launch.yml` both already use exactly that AVD, so the
  shared emulator matches the two repos that matter first. Other
  repos' AVD settings must be checked before they are added
  (findmy-mac / yt-player / moka-vpn / phone-node — not yet read).
- Per job: `adb install -r` the freshly built APK, then run the
  repo's own emulator test script with `TEST_SECTIONS=<scope>`
  (yt-client: `ci/emulator-launch-test.sh`). The emulator is never
  rebooted between jobs; if it dies, the server restarts it once and
  marks the affected job failed if the restart does not recover it.
- `none` scope skips the emulator entirely (build only), as in formal CI.

## Auth

Primary boundary: **tailnet membership**. The server listens only on
the runner's tailnet address, so only tailnet nodes can reach it at all.

Second layer: a bearer token, to keep a stray tailnet node from
driving builds. Recommended form (decision 2):

- **Option A (recommended): Moka-generated token via dispatch input.**
  Moka generates a random token, passes it as a `workflow_dispatch`
  input, the job reads it from the environment and never prints it,
  and Moka already knows it — no chicken-and-egg, nothing in the log.
  Residual risk: dispatch inputs are visible in the Actions run UI
  to repo viewers. Mitigation: the token is single-session, dies with
  the job, and is useless without tailnet membership.
- Option B: the job generates the token and Moka reads it from the
  run log. Same UI visibility, plus the extra step of fetching the
  log, so A is simpler.

Either way the token is never committed to the repo and never pasted
in chat — the same rule as `TS_AUTHKEY`.

## Cost

GitHub Actions minutes are free for public repositories, and
`ysk-agent/android-ci` is public, so a 1-hour session costs no
metered minutes on that basis. (Worth one confirmation against the
account's billing page before the first long session, since the
account also holds private repos.)

## Rollout

1. Implement `ci-session.yml` + `server.py` v1 for yt-client only.
2. One manual session: start, health-check, submit a `player`-scope
   job on a real commit, compare its wall time against the 4m14s
   formal-CI baseline and the ~1-minute `none` baseline.
3. Add repos one at a time (apps-updater next — same AVD), checking
   each repo's AVD and test script before adding it.
4. Layer 1 (commonised workflows) proceeds in parallel; the session
   server calls the same per-repo test scripts, so it benefits from
   that work without depending on it.

## Decisions needed from Yosuke

1. **Lifetime default:** 60 minutes — settled as activity-based
   (extended by testing in progress and by re-fetch; see Lifecycle).
   (Hard cap 360.)
2. **Auth:** Option A (Moka-generated token via dispatch input) or
   Option B (job-generated, read from the log)?
3. **Warm repos at start:** yt-client only (fast start, other repos
   pay checkout+build on first use), or warm all six up front
   (slow start, every later job fast)? moka-vpn's warm-up cost is
   the swing factor.
4. **Idle timeout:** superseded by the activity-based lifetime
   (decision 1) — no separate idle shutdown.
5. **APK retrieval:** fetch over the tailnet per job as proposed, or
   upload every job's APK as a GitHub artifact at session end?
